## Possibility-Driven Architecture: методология до кода

Перед первой строкой кода появился документ на 484 строки — **Possibility-Driven Architecture (PDA) v0.1**. Методология, которую я писал сам: как думать об архитектуре до выбора фреймворка.

PDA начинается с вопроса: **какую неопределённость система превращает в определённость — и за счёт каких устойчивых связей**. Не с ER-диаграммы.

Восемь шагов: карта неопределённости → акты определённости → граф домена → инварианты → константы → архитектурная сборка → наблюдаемость → стабилизация.

Для Founder Mode карта неопределённости выглядела так:

| Неопределённость | Акт определённости | Инвариант |
|---|---|---|
| Двигался ли я сегодня по главному? | Фиксация: yes / no / partial | Одна фиксация на дату на пользователя (INV-001) |
| Какой у меня приоритет? | Декларация в понедельник | Одна декларация на неделю |
| Что было на этой неделе? | Отчёт — LLM обобщает фиксации | Идемпотентность LLM-вызовов (INV-006) |
| Фиксация за будущий день? | Запрет валидатором | Фиксация только за прошедшие дни (INV-004) |

Из PDA в проект перешли три принципа, которые определили всё остальное:

1. **События фиксируют факты, домен обеспечивает инварианты, проекции оптимизируют чтение.** Три отдельных слоя, не смешанных.
2. **Инварианты — физика системы.** Они фиксируются до разработки и имеют механизм обеспечения: не пожелание, а constraint, валидатор или транзакция.
3. **Константы калибруются, а не придумываются.** Веса формулы ритма, окно в 14 будних дней, пороги токенов — всё это не с потолка.

К моменту релиза доки PDA устарели — код ушёл вперёд. Но база выдержала: event store, инварианты, проекции, наблюдаемость работают в проде ровно так, как было заложено.

## Стек: почему именно это

| Компонент | Выбор | Почему |
|---|---|---|
| Рантайм | Node.js ≥ 20, TypeScript (ESM) | Быстрый старт, единый язык для бота и рендера, зрелая экосистема |
| Бот-фреймворк | grammY | Лучший DX для Telegram-ботов на TypeScript: middleware, сессии, conversations из коробки |
| MAX-транспорт | Самописный адаптер (510 строк) | SDK MAX не существует; long polling, парсинг апдейтов, отправка — всё руками |

| LLM | OpenAI API (GPT-модель) | Стабильный API, предсказуемое качество для текстовой генерации карточек |
| Рендер карточек | Playwright (Chromium) → PNG | HTML/CSS → скриншот. Полный контроль над layout, шрифтами, масштабированием |
| Аватары | sharp | Resize, WebP, нормализация — одна библиотека без ImageMagick |
| Метрики | prom-client → Prometheus → Grafana | Стандарт индустрии; 8 кастомных метрик + дефолтные Node.js |
| Логи | pino + pino-pretty | Структурированный JSON в проде, человекочитаемый вывод в dev |
| Тесты | Vitest | Быстрый, TypeScript-native, совместим с ESM без хаков |
| Деплой | Docker, systemd на Selectel VDS (2 ядра, 4 ГБ) | Дешёво, предсказуемо, достаточно для одного пользователя и MVP |

Осознанное решение: **монолит**. Один процесс, одна база, один деплой. PDA явно предупреждает: «слишком ранние микросервисы ускоряют распад целостности». Для бота с одним пользователем любое разделение — оверинжиниринг.

## Event Store: append-only лог с идемпотентностью

Центр системы — таблица `events`. Append-only: ничего не обновляется, не удаляется. Семь типов событий:

```typescript
DeclarationCreated | DeclarationUpdated | PriorityChanged
ReportCreated      | ReportUpdated
FixationSubmitted  | UserRegistered
```

Каждое событие следует контракту PDA 4.4:

```typescript
interface BaseEvent {
  event_id: string;           // UUID
  event_type: EventType;
  occurred_at: string;        // ISO timestamp
  actor: { id: string; role: 'user' };
  subject: { entity: string; id: string };
  payload: EventPayload;
  causation_id: string | null;
  correlation_id: string | null;
  idempotency_key: string | null;
  schema_version: 1;
}
```

`causation_id` и `correlation_id` заложены в схему на будущее — когда появятся цепочки событий, трассировка уже будет работать.

### Идемпотентность: advisory lock + дедупликация

Если пользователь нажал кнопку дважды или бот перезапустился — дубликата быть не должно. Механизм — `pg_advisory_xact_lock`:

```typescript
await client.query('BEGIN');
if (partial.idempotency_key) {
  await client.query(
    'SELECT pg_advisory_xact_lock(42, hashtext($1::text))',
    [partial.idempotency_key]
  );
  const existing = await client.query(
    'SELECT ... FROM events WHERE idempotency_key = $1 LIMIT 1',
    [partial.idempotency_key]
  );
  if (existing.rows.length > 0) {
    await client.query('COMMIT');
    return rowToDomainEvent(existing.rows[0]);
  }
}
// ... INSERT и COMMIT
```

Почему advisory lock, а не `ON CONFLICT`? Append-only лог не обновляется — нужен не upsert, а **сериализация**: «подожди, проверь дубликат, потом вставляй». Lock отпускается автоматически при `COMMIT` / `ROLLBACK`. Два конкурентных запроса с одним ключом встанут в очередь — первый вставит, второй вернёт существующую строку.

## Domain Layer: валидаторы и инварианты

Домен — чистая логика без I/O. Валидаторы либо пропускают, либо выбрасывают `InvariantViolationError`:

```typescript
// INV-004: фиксация только за прошедшие дни
validateFixationDate(dateStr, todayStr)

// INV-008: обязательные поля зависят от ветки движения
validateFixationBranch(branch, fields)
```

`InvariantViolationError` несёт `invariantId` (`004`, `008`). В обработчике — понятное сообщение пользователю + инкремент `invariant_violations_total{invariant_id="004"}`.

Инварианты, обеспеченные на уровне БД:
- **INV-001**: `PRIMARY KEY (user_id, date)` в `daily_fixations` — одна фиксация на дату.
- **INV-006**: уникальный частичный индекс `idx_events_idempotency ON events(idempotency_key) WHERE idempotency_key IS NOT NULL`.
- Constraint `users_at_least_one_channel CHECK (tg_id IS NOT NULL OR max_id IS NOT NULL)` — пользователь не может существовать без привязки к каналу.

Инварианты, обеспеченные в коде:
- **INV-004**: валидатор `validateFixationDate()`.
- **INV-008**: валидатор `validateFixationBranch()`.
- **INV-006** (полный цикл): advisory lock в event store + `idempotency_cache` для LLM-ответов.

## Проекторы: CQRS-lite

Запись и чтение разделены. Запись — в event store. Чтение — из пяти проекций:

| Read Model | Источник событий | PK |
|---|---|---|
| `weekly_declarations` | DeclarationCreated / Updated | (user_id, week_id) |
| `weekly_reports` | ReportCreated / Updated | (user_id, week_id) |
| `daily_fixations` | FixationSubmitted | (user_id, date) |
| `weekly_priority_changes` | PriorityChanged | (user_id, week_id) |
| `users` | UserRegistered | user_id |

Проектор — `handleEvent(event)` с маршрутизацией по `event_type`, вызывается последовательно в той же async-цепочке после `eventStore.append()`. Не отдельный воркер — для одного процесса избыточно.

Важный нюанс: `eventStore.append()` делает `COMMIT`, а проектор вызывается уже после — в той же цепочке `await`, но за пределами транзакции. Если процесс упадёт между двумя операциями, событие в `events` будет, а read model — нет. Это известный паттерн «at-least-once»; исправляется пересборкой проекций из event log вручную. Для текущего масштаба этот сценарий практически невозможен.

## Два транспорта, один dispatch

Telegram и MAX (VK-мессенджер) — два API, два формата апдейтов, один набор хэндлеров.

**Telegram** — grammY: middleware, sessions, conversations. `registerHandlers()` подключает команды и callback-кнопки к `handle*`-функциям.

**MAX** — самописный адаптер: long polling, парсинг, отправка через `max-send.ts`. После парсинга — `dispatch(ctx, event, deps)`, единый роутер.

Общий контракт — `AppContext`: `reply()`, `replyImage()`, `session`, `getAvatarDataUrl()`. Хэндлеры не знают, откуда пришёл запрос.

MAX-адаптер — 510 строк, больше всего Telegram-транспорта. Документация минимальна: `user_id` на четырёх уровнях вложенности, аватары через пять URL-паттернов (ни один не стабилен), callback без sender. Решено кэшированием, фоллбэками и защитным парсингом.

## LLM: генерация текста с идемпотентностью

Четыре типа карточек: declaration, fixation, report, change. Каждый вызов — системный промпт (25–35 строк Markdown) + данные пользователя → связный текст. Стиль: «конкретно, без пафоса, без эмодзи, не выдумывай факты». LLM переформулирует введённые данные — не генерирует новые.

Двухуровневая идемпотентность:
1. **`idempotency_cache`** — кэш ответов LLM с TTL. Повторный вызов с тем же ключом не уходит в OpenAI.
2. **Event store** — даже если кэш протух, advisory lock не даст создать дубликат события.

Аудит: каждый вызов записывается в таблицу `llm_calls` — модель, токены in/out, latency, trace_id, user_id.

## Карточки: HTML → Playwright → PNG

Каждое действие генерирует карточку — PNG с аватаром, бейджем ритма и текстом. Четыре HTML-шаблона, плейсхолдеры `{{USERNAME}}`, `{{CONTENT}}`, `{{RHYTHM_BADGE}}`.

Пайплайн:
1. Сервис собирает данные (декларация, фиксация, отчёт, смена приоритета).
2. `build*CardHtml()` подставляет данные в шаблон, вшивает шрифт Roboto как data URL.
3. `renderCardPngWithPresets()` открывает Chromium через Playwright, рендерит HTML, делает скриншот элемента `.board`.
4. Если текст не влезает — автомасштаб: перебор пресетов, затем шаги масштабирования `[0.9, 0.82, 0.74, 0.66, 0.58]`.
5. PNG отправляется в чат.

Аватар — через `avatar-resolver.ts`: три режима (`uploaded`, `messenger`, `default`), нормализация через sharp (WebP, resize).

Узкое место при росте аудитории: каждый рендер — Chromium-процесс. Несколько одновременных запросов дадут memory spike на VDS с 4 ГБ. На текущем масштабе (один-несколько пользователей) не проблема; при командном использовании потребуется либо очередь рендера, либо вынос Playwright в отдельный сервис.

## Ритм: формула с тремя компонентами

Ритм (0–100) — не оценка личности, а метрика темпа и управляемости. Окно — 14 последних будних дней.

```
score = round((0.45 × flow + 0.25 × completion + 0.30 × stability) × 100)
```

**Flow** (0..1): среднее качество движения за окно. Веса дней: `yes = 1`, `partial = 0.7`, `no = 0.4`, `missing = 0.4`. Нормализация от `FLOW_MIN (0.4)` до `FLOW_MAX (1.0)`.

**Completion** (0 или 1): есть ли отчёт за текущую или предыдущую неделю. Бинарный — либо есть, либо нет.

**Stability** (0..1): суффикс от конца окна — сколько дней подряд без движения (`no` или `missing`). Два дня — норма (1.0). Пять и больше — распад (0.0). Между ними — линейная интерполяция: `1 - (streak - 2) / 3`.

Почему `missing = 0.4`, а не `0`? Отсутствие фиксации — «забыл или выходной», не катастрофа. Ноль обнулил бы flow слишком агрессивно.

Снимки ритма сохраняются в `rhythm_snapshots` при рендере карточки (не через проектор) — для отслеживания динамики скора по дням.

## Наблюдаемость: 8 кастомных метрик

PDA требует измерять не только рост, но и устойчивость. Восемь кастомных метрик:

| Метрика | Тип | Что измеряет |
|---|---|---|
| `invariant_violations_total` | Counter | Нарушения инвариантов (label: invariant_id) |
| `llm_calls_total` | Counter | LLM-вызовы (labels: model, cache_hit, type) |
| `llm_call_latency_seconds` | Histogram | Латентность LLM (buckets: 0.5–30 сек) |
| `funnel_started_total` | Counter | Начало воронки (label: type) |
| `funnel_completed_total` | Counter | Завершение воронки |
| `bot_opens_total` | Counter | /start |
| `card_edit_clicks_total` | Counter | Клики «Редактировать» (label: kind) |
| `experiment_started_total` | Counter | Эксперимент: CTA «Да» |

Плюс дефолтные метрики Node.js: event loop lag, heap, GC.

### Token spike detection

`token-spike.ts`: сумма `tokens_in + tokens_out` из `llm_calls` за скользящее окно. Порог из конфига, кулдаун 30 минут, алерт в Telegram/MAX. Защита бюджета: если промпт сломался или бот зациклился — спайк виден до неприятного счёта от OpenAI.

## Схема БД: 11 таблиц, одна миграция

Единая консолидированная миграция `001_init.sql` — 166 строк:

```
events                     — append-only лог (PDA Event Core)
users                      — user_id + tg_id / max_id
user_settings              — таймзона, уведомления, аватар
weeks                      — справочник недель
weekly_declarations        — read model
weekly_reports             — read model
daily_fixations            — read model (INV-001: PK user_id, date)
weekly_priority_changes    — read model
rhythm_snapshots           — снимки ритма (score + компоненты)
llm_calls                  — аудит LLM (INV-006)
idempotency_cache          — кэш идемпотентности с TTL
```

Плюс `002_service_error_incidents.sql` — таблица инцидентов для мониторинга ошибок по каналам.

Одна миграция — сознательно. За три недели схема переписывалась семь раз (reflection → fixation, plan → declaration). Проще пересобрать с нуля, чем писать ALTER. Консолидация — когда схема стабилизировалась.

## Тесты: 27 файлов, 1 992 строки

При ИИ-разработке тесты — единственная страховка от регрессий. Модель рефакторит 15 файлов за коммит — проверить каждую строку невозможно. Три слоя:

**Интеграционные** — реальная PostgreSQL (docker-compose test instance), полный цикл: сервис → event store → проектор → read model.
- `services.test.ts` (480 строк): declaration → fixation → report, мок LLM, проверка INV-001 и INV-004.
- `event-store.test.ts`: идемпотентный append — дубликат не создаёт вторую строку.
- `projectors.test.ts`: каждый тип события проецируется в правильную read-model таблицу.

**Доменные** — чистая логика без базы.
- `rhythm-score.test.ts`: формула ритма на граничных случаях — пустое окно, все yes, все no, streak ровно 2, streak ровно 5.
- `validators.test.ts`: INV-004 (будущая дата), INV-008 (неполные поля по ветке).

**UI / интеграция с ботом:**
- `dispatch-idle-unknown-command.test.ts`: что происходит при неизвестной команде.
- `notification-logic.test.ts`: логика расписания напоминаний.
- `card-render-*.test.ts`: рендер карточек не падает на граничных данных.

## Конфигурация: YAML + env

`config/default.yaml` — константы, которые PDA называет «поверхностями управления»:

- **reliability**: таймаут LLM, количество ретраев, TTL кэша идемпотентности.
- **observability**: порог токен-спайка, окно агрегации.
- **avatars**: директория хранения, лимиты размера.

Секреты (`DATABASE_URL`, `BOT_TOKEN`, `OPENAI_API_KEY`) — в `.env`, читаются через `dotenv`.

## Что PDA дала, а что — нет

**Дала:**
- Инварианты до кода — ни разу не пришлось «чинить» целостность данных в проде.
- Event store — полная история; можно пересобрать любой read model.
- Чёткое разделение слоёв — рефакторинг карточек не трогает домен, смена транспорта не трогает сервисы.
- Наблюдаемость — инцидент поймал, нейтрализовал, и сообщил пользователю о фиксе за 3 часа.

**Не дала:**
- Скорость. 484 строки методологии перед первым коммитом — перфекционизм. Половина артефактов не пригодилась для MVP.
- Код ушёл от доков за три дня.
- Рефакторинг reflection → fixation → declaration мог быть быстрее без попытки «сделать правильно» до понимания, что правильно.
